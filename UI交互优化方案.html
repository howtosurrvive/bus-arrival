UI 交互优化方案

参考 mouse-lin/finesse-skill · 对照公交到站老人版 V1.0 · 2026-10-30

先把结论说在前面。那个项目里真正能用的只有四份文档：移动端硬底线、H5 结构、手势响应、以及"怎么说人话"。 它的主体是一套做营销页的审美体系，和我们给 85 岁老人做工具的方向基本相反，那部分不该搬。

实际对照下来，我们最该改的不是"加动效"，而是一件听起来很土的事：到站卡片每 15 秒会把整页重绘一次，中间闪一下"正在查车…"，列表还会滚回原位。 这条比任何视觉优化都重要。

一、这个项目是什么

先说事实，避免把它的定位搞错。它不是模板库，也不是组件库，是一套写给 AI 看的设计规范——一个 skill 包。

项目内容
仓库mouse-lin/finesse-skill，HTML 项目，912 stars，昨天还在更新
形态一套 skill：SKILL.md（77KB 主索引）+ 30 份 references/ 分册 + 20 多个 examples/ 实战页
同一份内容复制进 .claude / .codebuddy / .doubao / .trae 四个目录，适配不同 AI 客户端
面向落地页、产品站、后台控制台、H5 活动页——以"让人眼前一亮"为目标
典型评审项SOUL（风格突出度）、SPECTACLE（动效强度）、DENSITY（信息密度）、anti-cheap（一眼 AI 感黑名单）

它最值得学的地方，是把"感觉"翻译成了可执行的规则。比如"这个弹窗很廉价"这种话没法执行，它会写成"如果整个交互就是 classList.toggle('on') 加一个 CSS 过渡，手指只是在启动一个计时器"——这就可执行了。

二、它真正有用的六条主张

从四份文档里挑出跟"手机上天天用的工具"直接相关的，其余（3D、hero 动效、渐变审美）略过。

1. 只有 class 切换的交互，一眼被看穿

出处：interaction-motion.md §1。它把"输入的不确定性"拆成四种——速度（是放过去的还是甩出去的）、方向（横划还是竖滚）、阈值（轻点、拖动还是甩）、掉帧（浏览器把 5 个事件合并成 1 个）。处理不了这四种的，就不算手势，只是个"穿着动画外衣的开关"。

对我们：设置面板现在正是这个状态——点击加 class，CSS 过渡把面板推上去。手指不参与任何决定。

2. 跟手四步，顺序不能换

出处：同上 §2。1:1 位移 → 越界阻尼 → 阈值 → 吸附。几个容易做错的细节：

  • 跟手必须严格 1:1。乘 0.85 这种"柔化"会被读成卡顿，而不是顺滑。
  • 拖拽时必须摘掉 transition，否则每一帧都排队进缓动曲线，跟手就没了。
  • 速度要用 100ms 滑动窗口。单帧瞬时值会飙到 12px/ms 的噪声；全程平均值会把最后那一甩稀释掉。文档里有实测：同一次 40px 拖动，瞬时算 12.00，窗口算 1.02。
  • 松手判定的条件是"距离 或 速度"，不能只取其一。只判距离 → "我甩了它却弹回来"；只判速度 → "我慢慢拖到底它却不动"。

3. 面板是五个决定，不是一个

出处：同上 §3。出身（从下面上来还是从中心放大——这是两种东西）、层次（后面的页面要"退后"，不是"变暗"）、控制器（能不能拖回去）、档位（吸附到最近的一档，绝不停在半路）、去向（展开成全屏是一个进度驱动四个属性）。

其中"层次"这条最反直觉，也最有用：深度是靠模糊和后退读出来的，只压黑会让人以为"那一层被禁用了"。

4. 移动端六条硬底线

出处：mobile-floor.md。它明说这些不是偏好，违反了页面不是"差一点"，是"看着像坏了"。跟我们有关系的四条：

编号规则为什么
M1overflow-x: clip（不是 hidden）hidden 会生成滚动容器，把 sticky/fixed 全部废掉
M2含图的栅格用 minmax(0,1fr)裸 1fr 的最小值是内容的 max-content，会把页面撑宽
M3按钮文字在任何宽度都不折行折两行的按钮读起来像做错了，不像设计选择
M4大标题加 overflow-wrap:anywhere长串不换行的名字在 320px 上一定溢出

5. 拇指区把页面上下颠倒

出处：h5-mobile.md §2.C。844px 高的屏幕，拇指舒服够到的是下面 55%。所以主操作放底部，顶部只放展示（标题、大数字）。返回按钮在左上角是唯一被接受的例外——肌肉记忆压过可达性。

对我们：这条我们做对了。大数字在上（看），两个按钮在下（点）。

6. 说人话：术语第一次出现要跟一句解释

出处：plain-words.md。核心是一句：用户要能判断，才叫确认；判断不了就只能说"看着还行"。它甚至列了一张对照表，比如 touch target 要写成"按钮实际能点到的范围，太小手指会点不中"。

对我们：这条对"给老人写的界面文案"同样成立，而且更重要——她不会问，她只会不用。

三、我们现在的实际状况

下面每一条都对着代码核过，不是凭印象。

四、该借鉴的，和不该借鉴的

这一节是整个评估里最需要克制的部分。那个项目的审美取向是"让人记住"，我们的是"让人不用想"。硬搬会出事。

值得借鉴

  • 刷新只改变化的部分——它整套文档都反对"中间白帧"和"整块重绘"
  • 按压必须有反馈（:active），手机上这是唯一的即时回应
  • 44px 触控底线，对老人要再放宽
  • 面板要有把手——不是装饰，是"这东西能拖"的唯一提示
  • 遮罩要后退不要压黑——"页面还在，只是退到后面了"
  • 安全区——底部手势条会盖住按钮
  • 说人话——第一次出现的概念要跟一句解释

不该借鉴

  • 加噪点、避免纯白——它的 anti-cheap 说大色块要加一层噪点才不"塑料"。对老人这是降清晰度
  • SPECTACLE / hero 动效 / 3D 引擎——它整套在评"视觉有多动"，我们越静越好
  • 大圆角 28–30px、玻璃拟态——观感取向不同，且玻璃会削弱对比度
  • 全大写小字 eyebrow——中文没有这个概念
  • FLIP 转场、多档位面板、滑动返回——见第五节 P2，对老人收益接近零
  • 横幅式 P0/P1/P2 评审话术——它面向的是"要不要上线"，我们面向的是"她能不能用"

五、优化方案

按"对她实际使用的影响"排，不按"技术上先不先进"排。每条都给了具体改法和成本。

P0 · 现在就能感觉到的问题

P0-1

静默刷新：别再每 15 秒重画一次

这是目前最影响体验的一条。现象：老人盯着「9 分钟」看，15 秒后整页变成"正在查车…"再变回来，站点列表还会重新滚到"你在这"那一行。如果她正往下翻看后面几站，会被拽回去。

证据：viewBoard() 首行 el.innerHTML = '<div class="loading">…'； setInterval(…viewBoard…, 15000)；接口实测 0.12–0.27s（弱网会更久）； 刷新后无条件调 centerMyStop()，滚动位置被重算。

改法：把"首屏渲染"和"后台刷新"分开。第一次进来照旧显示 loading；之后每 15 秒走静默通道——只更新变了的那几个节点，不重建列表。

// 现在的写法：每次刷新都是全新一页
function viewBoard(line, dir, station){
  el.innerHTML = '<div class="loading">正在查车…</div>';   // ← 每 15 秒都执行
  api(...).then(p => { el.innerHTML = 拼整页(); centerMyStop(); });
}

// 改成：首屏走原来的路，刷新只贴数据
function viewBoard(line, dir, station, silent){
  if(!silent) el.innerHTML = '<div class="loading">正在查车…</div>';
  api(...).then(p => {
    if(!p.ok){ return; }
    if(silent && paintBoard(p)) return;   // 只改字，不重建 DOM
    el.innerHTML = 拼整页();
  });
}

// paintBoard 只做三件事：大数字、每行状态、左上时间
function paintBoard(p){
  var n = document.getElementById("bigNum");
  if(!n) return false;
  setText("bigNum", p.main.minutes);          // 变了才加 transition
  setText("stLeft", "还有 " + p.main.stations + " 站");
  setText("clock",  p.updated);
  p.win.rows.forEach(r => {                   // 只动有车的行
    var row = box.querySelector('.swrow[data-i="' + r.i + '"]');
    if(row) row.classList.toggle("bus", !!r.bus);
  });
  // 不调 centerMyStop()：她滚到哪就是哪
  return true;
}

预期效果：画面不再闪；她往下翻看后面站点时不会被打断；选中站和滚动位置天然保持（DOM 没动）。
成本：中。要重排 homeCard() 的返回结构，给几个关键节点加 id。约 60–80 行。
风险：线路、方向、站台变了的时候必须退回首屏路径（用 _watch 比对即可）。

P0-2

底部两个大按钮，点了没反应

「这站的车」「念一遍」是整页最常点的两个东西，但 .btn 既没有 :active 也没有 transition。老人点下去，屏幕一动不动，她会以为没点中，于是连点三下。

改法：一行 CSS，加在皮肤里（三套配色一起生效）。

.btn{
  transition:transform .12s ease, filter .12s ease;
  -webkit-tap-highlight-color:transparent;
}
.btn:active{ transform:scale(.975); filter:brightness(.96); }
/* 老年人手抖，按压时长可能很短；.12s 比常规 .2s 更跟手 */

预期效果：点下去有一点点内缩，手指立刻知道"收到了"。
成本：3 行。风险为零。

P0-3

站点行 42px，比底线少 2px

规范底线是 44×44。老人手指接触面比年轻人大，2px 的差距在"边走路边点"的时候会放大成点错行——点到了错误的站，看到的是另一个站的到站时间，比点不中更糟。

改法：行高 42 → 46。JS 里两处 offsetHeight || 42 的兜底值同步改掉，其余计算本来就读实测高度，会自动跟上。

.swrow{ height:46px }        /* 106 行，原 42px */
var rowH = me.offsetHeight || 46;   /* 1241 行 */
var rowH = el.offsetHeight || 46;   /* 1421 行 */

预期效果：点中率上升，误触相邻行的情况减少。
成本：3 处改动。列表是固定高度的滚动窗口，行变高只影响"一屏能看几站"（40 站窗口从 9 行变 8 行），可接受。

P0-4

底部按钮会被手势条压住

我们设了 viewport-fit=cover，但 CSS 里 env(safe-area-inset-*) 一处都没用。在 iPhone 和带手势条的安卓机上，底部那条 34px 的横条会盖住 .btnrow 只有 18px 的下边距——「念一遍」按钮的下沿正好被压在下面。

改法：用 max() 兜底，支持的设备拿安全区，不支持的回落到原值——渐进增强，不会更差。

.btnrow{ padding:10px 14px max(18px, env(safe-area-inset-bottom)) }
.sheet { padding-bottom:calc(env(safe-area-inset-bottom) + 20px) }
.nav   { padding-top:max(19px, env(safe-area-inset-top)) }
/* 安卓 WebView 里 env() 可能返回 0，max() 会退回原值，不亏 */

预期效果：全面屏手机上按钮不再被压。
成本：3 行。注意：安卓壳里 WebView 在状态栏下方，顶部这条收益不确定，底部这条确定有用。

P1 · 明显更像"一个 App"

P1-1

设置面板：加把手、能下滑关掉、后面那层退后

现在这个面板只能点遮罩关，没有任何"能拖"的提示。规范里说得很直接：一个只能靠遮罩或 X 关掉的面板，就是一个圆了角的对话框。

改法分三步，可以只做前两步：

  1. 加把手（42×4px，圆角，14% 墨色）。成本 5 行，效果立竿见影——她看见那根小横条就知道能往下推。
  2. 后面那层退后：打开时给页面 scale(.96) + brightness(.96)，而不是只压黑。规范的解释是"只压黑会让人以为那一层被禁用了，而不是退到后面去了"。对老人尤其重要——她会以为坏了。
  3. 可以往下拖：跟手 1:1、越界阻尼、松手用"距离超过 1/4 或速度超过 0.5px/ms"两个条件任一成立就关。这一段就是规范 §2 的完整实现，约 60 行。
/* 把手 */
.sheet::before{
  content:"";display:block;width:42px;height:4px;border-radius:99px;
  background:rgba(26,28,30,.14);margin:-8px auto 10px;
}
/* 后面那层退后，而不是只变暗 */
#app.back{ transform:scale(.96); filter:brightness(.96);
           transition:transform .32s, filter .32s; }

预期：面板第一次真正"像 App 弹出来的"，而不是网页上浮出来一块。
成本：第 1、2 步各 5 分钟；第 3 步约 1 小时。建议：先做 1+2，观察老太太会不会去拖；会拖再加第 3 步。

P1-2

换页别硬切，给 120ms 的进入

现在从首页点一条线，整页 innerHTML 直接换掉。规范把这种情况叫"中间那一帧空白"——它等于在说"这是两件不相关的事"。老人会觉得"我刚才那页没了"。

改法：不做 FLIP（见 P2），只给新内容一个极轻的进入：位移 10px + 淡入 120ms。关键是快——超过 200ms 老人会觉得卡。

@keyframes enter{ from{opacity:.4;transform:translateY(10px)} to{opacity:1;transform:none} }
#app > *{ animation:enter .12s ease-out both }
@media (prefers-reduced-motion:reduce){ #app > *{animation:none} }

预期：点击后是"翻开一页"而不是"闪一下换了个屏"。
成本：4 行。风险：动画期间点不到元素——120ms 内基本无感，可接受。

P1-3

数字变了，让她知道变了

车从 9 分钟变 8 分钟，现在是静默替换。她可能正低头看站牌，抬头时不知道这数是不是新的；也可能以为刚才看错了。这是"到站提醒"之外最便宜的一条安心感。

改法：只在数字下降时给一次轻微的高亮（不是跳动——跳动会让人以为出错了）。

function setBig(v){
  var el = document.getElementById("bigNum");
  if(el.textContent === String(v)) return;
  el.textContent = v;
  el.classList.remove("bump"); void el.offsetWidth;   // 强制重排，动画才能重播
  el.classList.add("bump");
}
.bump{ animation:bump .5s ease-out }
@keyframes bump{ 0%{color:#1F9E5A} 100%{color:inherit} }

预期：数字一变，颜色轻轻一变再回来，眼睛会捕捉到。
成本：8 行。依赖：P0-1 做完才有意义（整页重绘时动画会重播，反而乱）。

P2 · 评估后建议不做

P2-1

FLIP 转场（卡片从列表项里"长出来"）

规范里有一整套实现，效果确实高级。但它是给"看图看物件"的场景用的——照片、商品卡。我们点的是一个数字列表项，长出来的过程没有信息增量，反而把"我已经到详情页了"这个认知拖慢 400ms。老人不需要这个。

结论：不做。P1-2 的 120ms 已经解决了"白帧"这个真问题。

P2-2

多档位面板、滑动返回

多档位（半开/全开）是为内容多的面板准备的，我们面板就 500px 高，一档到底。滑动返回是安卓系统手势，我们没拦它，本来就能用——再加一层自己实现反而会和系统打架。

结论：不做。

P2-3

11px 徽章提到 12px

「你在这」「车」「终点」这类小徽章现在是 11–11.5px，全项目 8 处。规范说 11px 在便宜屏上读不了。但它们不是信息主体，位置和颜色已经说明一切，涨到 12px 只是顺手。放在最后做。

成本：8 处数字改动。

六、实施建议

分两次做，中间隔一次真机验证。别一次全改——老人用东西，一次变太多她会认不出。

批次内容大概工作量怎么验收
第一批 P0-1 静默刷新、P0-2 按钮按压、P0-3 行高 46、P0-4 安全区 半天 盯着卡片看 1 分钟：画面不该闪；往下翻到第 30 站，等 15 秒，不该被拽回去；按住底部按钮，该有内缩；全面屏手机上按钮不该被手势条压住
第二批 P1-1 面板把手 + 退后、P1-2 换页进入、P1-3 数字变化 一天（含面板拖拽则再加半天） 打开设置，第一眼该看到把手；面板打开时后面的页面该变小变模糊，不是单纯变暗；点一条线，不该有中间那一帧空白；数字变了该轻轻闪一下
