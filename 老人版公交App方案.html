老人版公交查询 App · 可行方案

需求起点：掌上公交弹窗广告过多 · 目标：无广告、易操作、功能不砍 · 2026-10-29

先说边界。拆包、反编译、去掉广告后重新签名分发别人的 APK，属于侵犯著作权。掌上公交是工信部备案的商业应用，实时数据来自厦门搜谷的商业接口，改包这条路法律上站不住，也不值得走。

能走的路是自己做一个：功能对齐、广告为零、专为老人设计。下面的方案全部基于这条路。

而且你的诉求有明文依据。工信部《移动互联网应用（APP）适老化通用设计规范》第 5.1.1 条：适老版界面、单独的适老版 APP 中严禁出现广告内容及插件，也不能随机出现广告或临时性的广告弹窗。

另有第 2.4 条：弹窗关闭按钮最小点击区域不得小于 44×44dp，且只可在左上、右上、中央底部。摇一摇跳转、关闭键只有 12dp 这两件事，按现行规范都是违规的。这条信息本身有用 —— 除了自己做，你也可以通过 12321 或工信部投诉渠道要求厂商整改。

01GitHub 上可以直接参考的项目

找了四个，按与本次需求的贴合度排序。第一个几乎是白送的。

xiaofeiTM233 / my-bus-app 最贴合 · 直接 fork

Flutter · Dart · 六端（Android / iOS / Windows / macOS / Linux / Web）

这是一个基于 Flutter 复刻掌上公交公开查询体验的开源客户端。查线路、看站牌、盯车辆、找附近站点、地图查车，功能与原版对齐。数据直连 h5.mygolbs.com 的公开查询接口，覆盖 565 个城市，不需要登录，不需要注册地图 key。

技术栈：provider + ChangeNotifier 管状态、dio 管网络、flutter_map + 高德栅格瓦片做地图（GCJ-02，零 key）、geolocator 定位并本地做 WGS84→GCJ-02 转换、shared_preferences 做持久化、Material 3。

它的接口层已经摸清了，这省掉最费时间的一步：

  • CMD103 线路拓扑（站点序列），按城市+线路+方向做内存缓存
  • CMD106 附近站点
  • CMD110 站点搜索　·　CMD114 线路搜索
  • CMD209 同名/反向站台换向

对我们意味着什么：不用从零逆向接口，不用自己实现站序推算。拿它的 MyBusClient 和到站信息解析器当底座，把 UI 层整个换掉就是老人版。它的架构可以直接抄，它的界面一个都不要留。

注意接口是厂商的，自用没问题，上架分发不行。这一点后面第 6 节展开。

OneBusAway / onebusaway-android 架构参考

Java 98% · 2753 commits · GPL · Google Play 有正式发布版

北美开源公交项目的官方安卓客户端，从 2010 年维护到现在。它做的事情是：客户端很薄，所有公交数据由服务端的 OBA API 提供，服务端再对接各城市的 GTFS / GTFS-Realtime 数据源。

值得学的只有一件事：分层的位置。它把"数据从哪来"彻底推到了服务端，客户端只认一套 OBA REST 协议。所以它一个 App 能服务几十个城市，换城市只是换服务器地址。

局限：国内没有 OBA 服务器，它的数据接不上，UI 也不适合老人。看它的 SYSTEM_ARCHITECTURE.md 就够了，别碰代码。

前者是高德地图 SDK 公交查询的 Flutter 封装（只实现了安卓），后者是北京的实时公交查询实战项目。现在直接依赖有风险，但看它们怎么调高德的公交接口、怎么组织站点数据结构，仍然省事。

02架构：三层，关键是数据层可换

整套设计里只有一个决定是真正重要的 —— 把"数据从哪来"和"界面怎么画"彻底切开。

原因是现实：公交实时数据的供应方随时会变。厂商封接口、政府平台上线、高德调整配额，任何一件发生，写死在 UI 里的代码就要重写一遍。做成适配器，换源只改一个文件。

abstract class TransitSource {
  Future<List<Stop>>      nearbyStops(LatLng pos, int radius);
  Future<List<BusLine>>   searchLine(String city, String keyword);
  Future<List<Arrival>>   arrivals(String stopId, String lineId);
  Future<TripPlan>        plan(LatLng from, LatLng to);
}

四个实现，按优先级：

实现数据来源取舍
MyGolbsSource h5.mygolbs.com 公开查询接口 565 城，最全，到站精度最好。仅限家庭自用，不对外分发。
AmapSource 高德开放平台 Web 服务 API 完全合规，有免费日配额（具体额度以控制台为准）。线路、站点、换乘数据可靠，但实时到站能力弱，部分城市没有。
GovOpenSource 各地公共数据开放平台 免费、合法、可长期用。烟台等城市已开放公交到站预报，走 X-Client-Id / X-Timestamp / X-Nonce / X-Signature 的 HMAC-SHA256 签名。缺点是城市覆盖零散，得逐个城市确认。
CacheSource 本地 SQLite 装饰器模式，包在任意数据源外面。缓存线路拓扑和站点表，断网时至少能看站序和首末班。

建议的组合：主源 MyGolbsSource（自用，拿精度），CacheSource 包在外面做兜底，AmapSource 只用来补线路静态信息和换乘。政府源等确认了城市再决定接不接。

能力层

四个纯查询，不持有状态，输入参数出结果。这样每个都能单独写单元测试，也不用为了改一个 bug 去理解整个 App。附近站点做距离排序并合并同名站台，到站预测把"剩余站数"换算成分钟（用该线路历史平均站间耗时，取不到就用 2 分钟/站兜底）。

表现层：两个模式，一套代码

长辈模式是默认，标准模式留给家里年轻人帮设置时用（加收藏、改城市）。不做两个 App，切换开关放在长辈模式首屏右上角的小齿轮里，长按 3 秒才出现 —— 避免老人误触。

04自我迭代方案

先说迭代的驱动力。这是整个方案里最容易做错的地方。

老人不会给你需求。他不会说"我希望字体再大 2sp"，也不会说"换乘入口太深"。他只会说"不好用"，然后把 App 删掉，回到原来的方式。所以迭代不能靠问，只能靠看 —— 看他手指停在哪、点空了哪里、什么时候开始皱眉。

卡点日志：唯一的一手数据

每次有人在真机上试，只记三件事，不多记：

  • 停在第几屏（打开 10 秒后还停在哪儿）
  • 手指点了哪里（点空了、点错了、还是犹豫了 3 秒才点）
  • 有没有出声（"这什么呀""怎么又跳了"这类自言自语，原话记下来）

这三条比任何问卷都准。一条"他在首屏看了 8 秒才敢点"比十句"我觉得还行"有用。

五轮迭代

V0.1
打通数据（1–2 天）目标：证明数据拿得到。验收标准是命令行能打印出温州 12 路的实时到站，不要求界面。主要风险在接口参数和城市编码。
V0.2
单线跑通（3 天）目标：一个页面、一条线路、能自动刷新。验收标准是装上手机显示分钟数，连续 5 分钟不崩。这一步故意用最丑的界面，不做任何视觉设计，避免把时间花在会推翻的东西上。
V0.3
长辈首屏（3 天）目标：到站卡 + 三格 + 语音播报。验收标准很具体 —— 家里老人第一次打开，30 秒内能说出"12 路还有几分钟"。说不出来就是失败，不管界面多好看。
V0.4
卡点收敛（2 周，反复）只改卡点，不加功能。每一轮改完让同一个人再试一次，看那个卡点有没有消失。
V1.0
装机（2 天）图标、名称、离线兜底、崩溃日志。图标要能一眼认出 —— 大号公交图形加"公交"两个字，别用抽象线条。

三条纪律

  1. 一次只改一个变量。同时改字号和布局，出了问题不知道是谁的错，等于白改一轮。
  2. 卡点没消失就不加新功能。V0.3 到 V0.4 之间最容易犯的错是"顺手把换乘也加上"——加完界面变复杂，卡点反而更多。
  3. 每个版本留一个能回退的 APK。老人用惯的版本被改坏，他不会反馈，他会直接不用。

我在这套循环里干什么

你不需要看代码，也不需要描述技术问题。你只需要描述现象：

  • "我妈打开之后愣了一会儿才点" → 我判断是首屏信息层级问题
  • "她点了个地方没反应" → 大概率是点击区不够大，我查那个控件尺寸
  • "她说字还是小" → 我不猜，直接把她手机截图的字号量出来对比

每一轮我给出一个能直接装的新 APK，你装上给她试，回来告诉我现象。这个循环能跑多快，取决于你反馈得多具体，不取决于我写代码多快。

05必须先知道的硬约束

最要紧的一条：iPhone 装不了。苹果不允许侧载。要装只有三条路 —— 99 美元/年的开发者账号配 TestFlight（证书 90 天过期一次，到期要重新发）、企业签名（不稳定，随时掉签）、或者越狱。所以第一个要确认的问题是：老人用的是什么手机。

如果是 iPhone，方案要改成「网页版」—— 用 Safari 打开一个网址，加到主屏幕，图标和体验接近 App，没有安装门槛，也没有证书问题。这条路完全可行，只是地图和语音能力弱一点。

约束实际情况与应对
不能上应用商店用厂商接口做的东西过不了审。定位就是家庭内部使用，直接发 APK。不要想着上架或分发，那会把自用变成商用侵权。
接口随时可能断这就是数据层要做适配器的原因。断了之后切高德或政府源，界面一行不改。平时让 CacheSource 保底，至少站序和首末班还在。
地图瓦片高德栅格瓦片可以零 key 直连，但属于非授权使用，请求量大可能被限流。老人版其实不需要大地图——他要的是"还有几分钟"，不是"车在哪"。地图可以只放在二级页，省掉这个风险。
首次配置老人不会自己加收藏。所以第一次必须由家里人配好：选城市、搜 2–3 条常用线路、存成"回家/菜场/医院"。配好之后他打开就能用。这个环节不能省。

07选型：做 App，不做小程序

结论直接给：安卓 APK，Flutter 一套代码，顺带出 Web 版。小程序留作第二期备选，现在不做。

不是因为小程序不好，是因为这个场景的胜负手就是步数——整份方案的第一原则。

小程序只在两件事上真赢：安装门槛和自动更新。但这两件事由家里人一次性解决——你第一次装好、配好三条线路，之后就固定了。而"步数"和"到站提醒"是每天都发生的，逃不掉。

别一次做两个。老人版最大的风险不是技术，是他不接受。先做一个跑通，让他真用上一周，再谈第二个入口。

而且 Flutter 一套代码能同时出 APK 和 H5——H5 加到桌面就是个"准 App"，可以当安装失败时的兜底，成本几乎为零。小程序要另写一套 WXML/WXSS，等于两份代码两份维护，现在不值得。

08语音和「导航」：需求要改

语音要做。但通用语音助手在老人场景是灾难，必须砍成有限指令集。

想象一下老人说："帮我看看那个去菜场的车还有多久。"ASR 转成文字没问题，接下来要做语义理解，理解错就要追问"您要查哪条线路？"——问一句就死。老人连错两次，这个功能他就再也不碰了。

正确做法是只做槽位匹配，不做语义理解：

语音输入识别方式匹配不到时
"36 路""三十六路""三六"正则提取数字 → 查线路表说"没听清，您再讲一遍"，同时把三个大按钮高亮，让他点
"回家""去菜场""去医院""去儿子家"预设目的地词表精确匹配

词汇表总共十来个词，成功率能上 90%。老人说错一次不会伤到他，因为界面本来就有兜底的大按钮。

ASR 选型：先用安卓系统自带 SpeechRecognizer（免费、不要 key、国产 ROM 都有），跑不赢再换讯飞 SDK。讯飞在中文口音和吴语方向上明显更强，离线版也免费，代价是包体变大、有装机量限制。先用免费的验证，别一上来就集成 SDK。

「自动搜索导航」这个需求，我建议改掉。老人说的"导航"和你理解的导航不是一回事——他要的不是地图上画一条蓝线，他要的是"我现在出门，赶不赶得上"。

下车提醒坐车时怕坐过站，尤其不常去的地方。快到站了震一下。同一套轮询，改个判断条件

至于地图导航，老人天天在同一个站坐车，闭着眼都走得到。地图只放在二级页，给"偶尔去陌生地方"兜底就够——顺带还省掉了高德瓦片被限流的风险（见第 5 节）。

方向判断：网页版有个硬限制，得说清楚

你要的「用定位判断他在哪一侧站台」，技术上查过了：石坦站两个站台相距 46 米，坐标是分开的，能按距离算。

但网页版有两个绕不过去的坎：

  • 局域网 http 下浏览器根本不给定位权限，只认 HTTPS 和 localhost。所以手机上打开网页时，GPS 拿不到
  • 就算拿到了，46 米的间距要求定位精度在 20 米内。在家里（离站几百米）根本判断不了，只有站在站台边上才准

所以这一版的做法是：主方向用「记住你上次坐哪个方向」，存在手机本地。点底部的「换个方向」会记住新的选择。这比 GPS 更可靠，因为老人出行高度规律——早上出门和晚上回家，方向和时段是绑死的。

等做成原生 App（有真正的定位权限），再把 GPS 加进来做二次校正：离站台 40 米内用定位纠正，超过就用历史习惯。

顺手修掉的三个坑

  • 「小于 1 分钟」被算成 1 分钟，会让老人以为还有 60 秒。现在归零，显示「马上到」
  • 「已到站」落到了兜底分支，显示成「稍后再看」。现在单独处理，显示「车在站上 / 快上车」
  • 站牌页整列渲染不出来。原因是拼接 onclick 时用 JSON.stringify 生成了双引号，把 HTML 属性提前截断，整行 DOM 被吞掉。改成先算完整 URL 再拼

下一步

现在功能结构完整了，可以开始收拾界面。但在动 UI 之前，建议你先在手机上把三个页面点一遍，重点看两件事：

  • 线路详情滚到石坦之后，上面那 28 个站她会不会去翻（不翻说明列表只需露出前后几站）
  • 站牌页那个「还有 24 条线」，她会不会点开（不点说明 6 条够了，甚至可以砍到 4 条）

这两条决定列表该多长，比调颜色重要得多。

10V0.4：搜索上线，轻轨只有站表

先说清楚之前为什么你看不到

我前几轮给的是 http://127.0.0.1:8765。127.0.0.1 是本机地址，只有运行服务的那台电脑能打开，换台设备或者预览面板里都进不去。这是我的疏忽。

现在改成：每一版都生成一个独立的 HTML 文件，数据已经内嵌在里面。双击就能打开，不需要服务、不需要联网、能直接发到手机上。

文件名规则：老人版公交_v版本号_演示.html。每改一版就出一个新的，你随时可以对比哪一版更好。当前是 v0.4。

文件里内置了 9 组真实数据快照，所以离线也能点。想查没内置的线路，会提示「演示版只内置了几个例子」——那是正常的，跑本地服务才能查全部。

搜索：线路和站点一起搜

首页底部多了「查线路」按钮。输入框很大（21px），按回车或点「搜」都行。结果分两组：

轻轨：能读到，但没有实时数据

结论：温州 S1、S2 线的站点表完整，实时到站是空的。

S1 线 18 站（双瓯大道 → 瓯华 → 瓯江口 → 灵昆 → 机场 → 永中 → 奥体中心 → 瑶溪 → 科技城 → 龙腾路 → 三垟湿地 → 惠民路 → 龙霞路 → 德政 → 新桥 → 动车南 → 潘桥 → 桐岭），S2 线（清东路 ↔ 东山）也在。

但接口返回的 hasReal 是 0，站牌查询里 neartext 和 neardis 两个字段全是空的，首末班时间也是空的。我又查了「科技城站（地铁站）」和「惠民路站（地铁站）」两个具体站点，返回都是空值，不是个别站点的问题。

所以轻轨只能做「站点顺序 + 换乘参考」，做不了「还有几分钟」。页面上已经如实处理：顶部有一条橙色提示「这条线没有实时到站数据，只能看站点顺序」，不会让人对着空白等。

如果以后确实要轻轨实时数据，只有两条路：一是等掌上公交接进来，二是去温州铁投的官方渠道找。都不是我们这边能解决的。

正确逻辑：index <= 我的站序 才表示还没到。改完之后，上行那辆已过站的车不再显示，下行的车正确标在第 10 站。

二、「车还在上面 14 站」这种说法不成立。「上面」是界面方位，不是真实位置，而且和上方的「还有 14 站」重复。改成直接报站名：「车现在在 市中西医结合医院」。老人对站名有概念，对「14 站」没有。
